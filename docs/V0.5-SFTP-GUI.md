# v0.5 SFTP GUI — Linux interactive auth review

Implemented: independent local/remote panels, explicit path/refresh/up and folder
navigation, selection, name/type/size/mtime/mode, binary upload/download,
confirmation, no-replace publication, byte progress and cancellation. SSH and SFTP
consoles stay mounted when switching tools. Opening tabs starts no operation.

## Transport and security

System OpenSSH `ssh -T -s … sftp` transports binary SFTP v3 packets. The structured
adapter follows the [protocol draft](https://www.openssh.org/txt/draft-ietf-secsh-filexfer-02.txt),
checks lengths, request IDs, attribute flags and UTF-8, and ignores `longname`.
It never parses CLI listings or interpolates filenames into shell commands.
No new dependency. OpenSSH verifies known_hosts including changed/revoked keys.
Configuration, shell commands, forwarding and multiplexing are disabled.

Linux Files now offers a native OpenSSH authentication bridge: select Auto,
Key/agent or Password/PAM in the Files login panel, connect, verify the host
fingerprint through a trusted channel if new, and enter credentials at the hidden
OpenSSH PTY prompt. Wait for “Authenticated — panes ready”, then load both panes.
The terminal deliberately has no shell prompt after successful login.

The bridge runs OpenSSH with ControlMaster=yes, ControlPersist=no and -N -T.
Its exclusive /tmp/nd-<UUID> directory is created with mode 0700. The socket is an
authenticated-session capability, not a credential file. The backend binds it to
the original host, port, username and live session; the frontend cannot provide
an arbitrary socket path. SFTP retains separate binary stdin/stdout pipes.
A false proxy makes a missing master fail closed, without fresh authentication
or a different connection. Disconnect/tab/window close kills the master; an
uncompleted auth prompt times out after 120 seconds. Abrupt crashes can leave an
empty directory/socket; no automatic broad /tmp cleanup is performed.

Host trust remains OpenSSH StrictHostKeyChecking=ask on the auth PTY, including
changed/revoked-key rejection; the direct key/agent path remains strict=yes.
No bypass or automatic acceptance. Trust is checked when the master connects;
an already established SSH session is not re-authenticated for each operation.
Passwords/OTP/passphrases pass transiently from the terminal input through Tauri
to the native PTY. They are not stored in React state, localStorage, files,
process arguments, environment, logs, commits or telemetry. JavaScript/OS buffers
cannot promise forensic memory erasure. The private socket authorizes access to
the same account until disconnect; same-user compromised processes are outside
the isolation boundary. No agent forwarding, shell command or remote PTY.

Windows interactive Files login is not implemented: uncheck the Linux login
option to use direct key/agent with previously trusted host keys. Existing
Windows SSH/SFTP password/PAM consoles remain available. Windows CI compiles and
tests this explicit limitation; it does not prove Windows interactive GUI auth.

Transfers use loaded paths, not unsent address-bar edits. Both panels must be
loaded. Explicit confirmation shows direction/name/destination; the backend also
enforces no-replace semantics, independently of stale listings. A profile edit
invalidates remote state. Closing the tab cancels its action; closing the window
kills/reaps registered children. Cancellation and timeout kill the process to
unblock pipe I/O. Cancellation cannot roll back an already committed publication.

Upload exclusively creates `.nodedesk-<UUID>.part` (0600), acknowledges every write,
checks size and closes before ordinary SFTP v3 RENAME. Per the protocol, rename
must fail if the final name exists; never use the overwriting posix-rename extension.
A failed/cancelled upload may leave this named partial; the error reports it.
Cleanup is manual through console, avoiding deletion of a replaced remote path.

Download rejects known symlinks/existing final names, writes a private exclusive
local partial, checks byte count, syncs and hard-links to the final name atomically
without replacement. RAII removes its local partial on success/failure/cancel.
A crash may leave a partial. Hard-link support (ext4/NTFS) is required; FAT/exFAT
fails safely. Permissions/mtime are not preserved. Same-length concurrent source
changes are not detected: hash-check files modified during a transfer.

## Limits and next work — issue #9 remains open

- Non-recursive mkdir and delete, no-overwrite rename and internal file drag/drop are now implemented in the review branch. No folder-tree view, recursive operations, overwrite,
  resume, queue, permission editing, remote editor or automatic updates.
- Windows GUI password/PAM bridge and a key-file picker remain deferred.
- Linux login uses an embedded auth terminal, not a separate password form.
- Each remote action opens a fresh SFTP channel; Linux interactive mode reuses
  the authenticated master. Direct key/agent mode reconnects. One operation per browser, 16 app-wide,
  120-second total timeout, 1 MiB packets, 10,000 directory entries. Limits fail
  explicitly; large directories are not silently truncated.
- Portable UTF-8 names including spaces/Unicode work. Controls, Win32 device
  names/reserved characters, separators, colon, trailing dot/space and non-UTF-8
  names fail closed. A remote unsupported name fails the listing; local unsupported
  names remain visible but disabled. Names are never lossily normalized.
- Symlink rows are visible but cannot be opened/transferred. Explicit path bars
  can resolve symlink directories. This is a filesystem client, **not a directory
  sandbox**. SFTP v3 has no atomic O_NOFOLLOW: a hostile server/concurrent remote
  writer can race LSTAT/OPEN. Client checks do not confine hostile writable parents.
- Backend diagnostics are English in both locales; controls/help/error context
  are RU/EN. Stderr is discarded, not logged; auth/trust/EOF errors are generic.
  Use the console to diagnose. Windows real-server integration remains manual.

Next: Windows interactive auth bridge, directory tree and extended DnD;
pagination; transfer queue/retry/resume; protocol-specific hostile-path hardening.
This PR does not close the complete #9 acceptance checklist.

## v0.5 follow-up: bounded filesystem mutations and internal drag-and-drop

In this review branch, both panes now provide New folder, Rename and Delete controls. Rename requires a previously loaded, selected regular file or directory; delete is **permanent** and requires explicit confirmation showing the filename, parent folder and the non-recoverable nature of the action. No recursive deletion, no symlink mutations, no copying directory trees. Remote SFTP v3 uses the actual MKDIR (14), RENAME (18), REMOVE (13) and RMDIR (15) requests. Server-side LSTAT revalidates the expected entry kind; rename checks that the new filename is absent and uses ordinary v3 RENAME, **never** the OpenSSH overwrite extension. RMDIR succeeds only for an empty remote directory. On SFTP servers that violate v3 semantics or under hostile concurrent writers, a pre-check is not a fully atomic universal no-overwrite guarantee; do not rename important files without backups.

Local mkdir uses create_dir; delete supports regular files and empty folders, refuses symlinks and non-matching entry types. Local regular-file rename uses exclusive hard_link + unlink to prevent destination clobber on supporting filesystems. Local **directory rename** now uses Linux renameat2(RENAME_NOREPLACE) and Windows MoveFileExW without REPLACE_EXISTING, never plain std::fs::rename (which could overwrite on Unix); unsupported kernels/filesystems fail closed. Directory move is same-volume only; the source can still change between an initial LSTAT and the syscall in an adversarial writable directory. Hardlink-based *file* rename is not an atomic move: if removing the old name fails, both names may remain. FAT/exFAT may reject hardlink operations.

Two-pane internal Drag & Drop transfers **single selected regular files** between *loaded* panes. The drop target and source directory are validated and the same explicit upload/download confirmation/no-overwrite check is used as the buttons. External OS file drops, directory recursion and bulk selection are unsupported. An incomplete upload can still leave a marked remote `.nodedesk-*.part` file; cancel cannot undo a committed mutation.

Tests: Rust local mutation tests include invalid names, existing-name collision, no-clobber, nonempty directories and type rejection. Real sshd SFTP integration verifies remote mkdir, rename, destination collision and nonrecursive delete in a disposable directory. Playwright UI contracts cover prompts, confirmation, readiness gating, existing-name rejection and internal drag collision. **Manual full GUI verification on Arch and Windows remains pending**; the existing verified Linux password/PAM fixture is not evidence of all graphical user flows.

## Automatic pane refresh after successful actions

After a successful upload/download or mkdir/rename/delete, NodeDesk invalidates
the destination listing and reloads **only that pane** from the backend. The
refresh is a separate, user-initiated-session operation after the mutation's
operation gate is released; it does not reopen a disconnected login or start
new sessions automatically. Cancelled, failed, stale-profile and unmounted
operations do **not** trigger a refresh. If the refresh itself fails, the pane
remains unloaded and the error is shown; the mutation is not repeated.

The other panel (including its selection) stays unchanged. This behavior is
covered by an additional Playwright contract test for upload and mkdir.

## File list searching and sorting

Each loaded file pane now has a **local, case-insensitive filename filter**.
Typing narrows the current listing without requesting a new SSH/SFTP
connection, and clears any selected row so a hidden item cannot be
accidentally uploaded, downloaded, renamed or deleted. Folders sort before
files/links, with natural numeric ordering among names. The full loaded
listing remains authoritative for backend operations and drag/drop checks.
The filter does not search the entire server filesystem or recursively
walk directories. The filter is not persisted in catalog profiles.

## Bounded multi-file transfer queue (new review slice)

The GUI can select multiple **regular files** in a loaded local or remote pane
using checkboxes (limit: 50 files per operation). The **Upload selected** and
**Download selected** actions confirm the complete batch before any transfer.
The client validates every selected name and aborts the entire queue if any
name collides in the currently loaded destination listing, is unsupported, is
not a regular file, or one pane is not loaded. The Rust backend also rechecks
paths, source types and destination exclusivity for **every** file.

Files transfer **sequentially**, never concurrently. The queue stops on the
first failed file or on cancellation and never silently skips or retries.
There is one progress bar for the current file plus a displayed item index.
The Cancel button requests cancellation of the active native operation and
prevents starting remaining files. Files already successfully published are
**not** rolled back; if the batch is interrupted after partial completion,
the destination listing is invalidated to avoid showing stale information.
A successful batch reloads only its destination pane. No queue persists or
resumes after the tab or app is closed, and no credentials or filenames are
persisted outside the existing catalog.

This is an intentionally small queue, **not** a background transfer manager:
no resume/retry, transfer history, bulk directory traversal, external OS file
drop, transfer speed aggregation or background priority controls.

Verification: pure-model tests cover collisions, limits, source types, duplicate
selection and non-mutating planning; Playwright UI contract tests cover two-file
sequential upload and cancel during the first file. CI also runs the existing
real-sshd binary transfer/host-trust fixture, but those UI queue tests use a
mock adapter and cannot prove real user-server GUI access. The latest CI and
manual Arch/Windows GUI acceptance are required before merge.

## Transfer queue outcomes and selected-file drag

The current review branch exposes a **session-only per-file report** with states
Queued, Transferring, Done, Failed, Cancelled and Not started (also translated
into Russian). Closing the tab or changing the connection discards the report;
it is never written to storage or telemetry. The current queue index now uses
the actual number and filename rather than the literal placeholder string.

For a batch, every file is still transferred sequentially with the existing
binary SFTP transport, no overwrite and explicit batch confirmation. On
cancellation, any unstarted files are marked **Not started**, not falsely
reported as successful. Successfully committed files remain in place and are
not rolled back. A failed item stops subsequent transfers; the user can
reload the destination before attempting another batch.

**Select visible (up to 50)** chooses eligible regular files from the currently
filtered listing. Dragging one of the chosen files to the opposite pane sends
the chosen set through the same bounded batch validation/confirmation path.
Dragging an unselected file sends only that one file. Invalid drag payloads,
same-pane drops, duplicate names and unsupported paths are rejected before
invoking the backend; the backend independently checks type and destination.

The report is not a durable transfer history, persistent transfer queue,
resumable job list or retry mechanism. Tests for the report/state transitions
and UI contract tests for cancellation, completion and multi-drag have been
added. Newest CI and final manual Arch/Windows desktop acceptance are required.

## Native Windows SFTP authentication capabilities

The app now queries the Rust backend for supported file authentication methods
via `files_capabilities`. On native Windows OpenSSH the interactive Unix
ControlMaster socket bridge is not available, so the GUI **defaults to
key/agent mode** and disables the unsupported password/PAM checkbox with
a clear RU/EN explanation. Password authentication remains available in the
separate SSH and SFTP *terminal* tabs (via a native PTY). Linux continues to
show interactive password/PAM in the Files panel by default.

No OS is inferred from the WebView user agent; the native backend reports
its actual capability. Neither path relaxes OpenSSH `known_hosts` trust.
The request does not collect, copy, cache, or log any credentials.
The capability check does not silently attempt password login or start a
network connection. Automated browser contracts cover Windows/Linux
presentation and ensure that Windows does not spawn an unsupported SSH
ControlMaster bridge. Rust tests verify capability flags.

This is a **safer fallback, not implementation of Windows GUI password**.
A real Windows password/PAM file browser needs an audited transport
architecture that does not depend on Unix ControlMaster or expose passwords
through arguments, environment variables, logs or persistent storage.
Relevant upstream design:
https://github.com/PowerShell/Win32-OpenSSH/wiki/About-Win32-OpenSSH-and-Design-Details
