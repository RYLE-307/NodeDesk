# NodeDesk v0.6 — system VPN profiles (draft PR #11)

## Scope

The System VPN / Системные VPN tool is a separate workspace tab, not a
host-and-port entry in the connection catalog. Opening the tab **only reads**
existing OS profiles. No VPN is started automatically.

The panel displays profile name, type, and the operating system's currently
reported connected/disconnected state. There is a manual Refresh action.
Connect and Disconnect always request confirmation, warning that routes,
DNS, and the user's current remote access can be interrupted.

### Supported platforms

- **Arch / Linux:** NetworkManager-managed VPN and WireGuard profiles.
  Requires NetworkManager and /usr/bin/nmcli. The backend identifies profiles
  by their OS-assigned UUID and uses explicit UUID operations through nmcli.
  It never guesses or modifies Wi-Fi/Ethernet profiles.
- **Windows 10/11:** current-user built-in Windows VPN phonebook profiles
  with IKEv2, SSTP, or L2TP and Required/Maximum encryption. Reads only
  the non-secret name, GUID, tunnel type, and ConnectionStatus fields via
  Get-VpnConnection. Uses rasdial.exe with the selected existing profile
  name to connect or disconnect. All-user phonebooks, PPTP, Automatic
  tunnel selection, optional/no encryption, and profiles managed by
  third-party clients are deliberately excluded in this slice.
- Windows credentials must already be configured with the OS, and Linux
  must have credentials or a supported NetworkManager secret agent.
  Missing credentials, required interactive authentication, or insufficient
  permissions can cause the action to fail; NodeDesk does not collect them.

## Trust and safety invariants

- NodeDesk does not import, export, generate, edit, store, or display VPN
  configuration files, EAP XML, PSK, private keys, passwords, or credentials.
- Only profile UUIDs read freshly from the operating system are accepted for
  connect/disconnect. The backend re-lists before acting, validates UUID
  syntax, and restricts Windows profile kinds. Browser input cannot select
  arbitrary executable paths, command arguments, hostnames, or routing tables.
- Uses absolute system executable paths and argument arrays without a shell.
  Windows PowerShell executes a constant read-only script for profile status.
  Command stderr/stdout containing possible sensitive system diagnostics
  is NOT exposed to the WebView, logs, or error messages.
- VPN routes and DNS change only via OS-controlled activation/deactivation
  after user confirmation. System policies, keychain agents, and VPN
  authentication remain with the OS. No automatic retry, background
  connection, profile modification, or fallback to insecure protocols.
- The UI displays OS-reported status, not independent proof of routing,
  leak resistance, VPN endpoint identity, or tunnel encryption. No
  automatic monitoring or changes after closing the NodeDesk tab.

## Verification

- Rust unit tests cover strict UUID and display-name validation, rejection
  of manipulated identifiers, and secret-field serialization exclusion.
- Playwright tests cover list-only behavior, no automatic VPN action,
  explicit confirm/cancel, successful state changes, errors, RU/EN and
  no fake profiles.
- Existing SSH/SFTP, RDP and VNC CI test suites are retained on Windows
  and Ubuntu. The system VPN integration is compiled on both platforms.
- The CI agents do not contain authorized production VPN profiles. A
  successful build/contract test is NOT evidence of a live VPN session.

## Manual acceptance (never on an essential production VPN first)

1. On Arch, confirm the user's disposable NetworkManager VPN/WireGuard
   profile is already configured and that NetworkManager is running.
   On Windows, use a disposable user-scope IKEv2/L2TP/SSTP profile.
2. Open System VPN, verify expected name/type/status and that no connection
   starts by itself. Confirm Refresh rereads the current OS state.
3. Click Connect, cancel in the confirmation dialog, verify no network action.
4. Approve Connect on the disposable test profile. Verify Windows/NetworkManager
   successfully authenticates using OS-managed credentials, and inspect
   routes/DNS and the OS connection status independently.
5. Approve Disconnect and verify traffic/routes revert as expected. Repeat
   RU/EN and tab close/reopen. Check failure states with missing credentials.
6. Verify unrelated SSH/SFTP sessions and remote access are not accidentally
   disrupted before using the feature on production hosts.
7. Leave PR #11 draft until user confirms both operating systems.

## Next iterations

Support richer OS VPN adapters (other Windows phonebooks and audited
third-party VPN applications), clearer authentication handoff, lifecycle
events, connection history without secrets, and VPN-before-SSH/RDP/VNC
orchestration. Never edit system routing policies without explicit consent.
