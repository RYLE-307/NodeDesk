# NodeDesk v0.3 SSH vertical slice

This branch adds a real OpenSSH process attached to a native PTY (Unix PTY / Windows ConPTY), rendered by xterm.js through Tauri IPC channels. No external terminal, shell wrapper, simulated connection, remote service, or automatic connection is used. Open a catalog tab, then explicitly press Connect. Authentication now offers Auto (key, keyboard-interactive, password), Key (key/agent only), and Password/PAM (keyboard-interactive/password only) in the SSH tab. Passwords, PAM prompts and encrypted key passphrases are entered directly into OpenSSH's native PTY at a non-echoing prompt. They are never saved by NodeDesk.

## Trust and secrets

OpenSSH uses the OS user's standard known_hosts (including hashed entries and revocation markers), with StrictHostKeyChecking=ask, UpdateHostKeys=no and VerifyHostKeyDNS=no. An unknown host requires explicit confirmation of its SHA256 fingerprint in the terminal. Verify it through a trusted independent channel before answering yes. A changed or revoked key is rejected; NodeDesk never deletes trust entries or offers an insecure override. No ssh-keyscan result is trusted for production connections.

The adapter uses argv without a shell and validates destination/user/port/size. It ignores ssh_config with -F none, disables forwarding, local commands, multiplexing and local escape commands. In Password/PAM and Auto modes, password and keyboard-interactive prompts are enabled with a three-prompt limit; in Key mode they remain disabled. Therefore aliases, custom IdentityFile, ProxyJump and ProxyCommand are intentionally unavailable. OpenSSH must be installed and trusted on PATH. The agent is local only, never forwarded. No credential is written to catalog/localStorage, argv, logs or Git. Password text may pass transiently through the webview-to-Rust IPC as terminal input; this feature is not a separate OS-protected password dialog. Use a trusted desktop environment. Never enable developer logs that record PTY input. Terminal output stays in memory (2000 lines); do not type secrets into commands that a remote shell will echo or store in history. There is no transcript recorder, telemetry or OS vault yet.

## Lifecycle and UI

Each open catalog SSH tab owns one terminal and at most one process. Hidden tabs stay mounted, retain output and keep their sessions. Split displays two different open tabs; selecting the same tab shows one terminal, not a second connection. Input is serialized, output is transported as bytes, PTY resize propagates to the server, and stdout/stderr are naturally merged by the PTY. Disconnect/cancel/close/delete/window destruction terminate the local SSH process. The reader thread reaps it. Late connection completion after cancellation is closed again. Reconnect is always explicit and creates a new session ID. Exit code and startup errors are visible. The UI says SSH started rather than claiming authentication succeeded; remote shell output is the evidence of successful authentication.

Limits: 16 simultaneous sessions, terminal 2–500 columns / 2–300 rows, 64 KiB per input message. No saved passwords, arbitrary key picker, SFTP, tunnels, session restoration, broadcast input, or separate stdout/stderr panes. OS OpenSSH prompts remain in its installed language; NodeDesk controls/help are RU/EN. Terminal uses a fixed dark palette inside the existing light/dark/system application. A slow frontend can accumulate queued IPC output: sustained bulk-output backpressure remains future work. Windows ConPTY and agent/passphrase behavior still require manual verification on a real installation.

## Automated checks

Frontend tests/build run on Linux and Windows. Desktop CI runs Rust tests and a Tauri no-bundle build on both OSes. Linux additionally starts an isolated loopback sshd with generated ephemeral keys: tests reject an unknown key, explicitly approve it, reuse known trust, reject a changed key and a revoked key. Rust tests validate argument injection, secure options, dimensions and killing/reaping a PTY child on session drop. Cargo.lock and package-lock.json are committed. Missing local Rust or desktop runtime does not count as a passed desktop test. Manual Arch/Windows interaction and authentication remain required.

## Password/PAM acceptance (added after Arch feedback)

- Select **Password / PAM** in a tab to disable public-key attempts and allow OpenSSH's hidden password/keyboard-interactive prompts. **Auto** tries keys first, then keyboard-interactive/password; **Key** retains the original key-only behavior. Selection is per open tab and not persisted.
- Confirm the server's SHA256 host key via a trusted independent source *before* typing a password. Unknown keys require explicit acceptance; changed and revoked keys are rejected. A correct password is not evidence of trusted host identity.
- Verify correct password, wrong password (max three prompts), cancel during prompt, reconnect, expired/locked account, PAM keyboard-interactive and 2FA prompts on an isolated test host. No real password should be sent in chat/log output.
- Type at the OpenSSH PTY password prompt: normally **nothing is echoed**, including asterisks; hit Enter to submit. NodeDesk does not save credentials. No auth setting bypasses host key trust.
- Linux and Windows PTY/ConPTY password prompt behavior must each be manually verified. The existing Linux CI fixture tests host keys with key auth; password/PAM integration is not yet covered by that fixture and must not be described as CI-proven end-to-end.

## 2026-11-18 — queued terminal input and session identity

The xterm input queue checks the current native session ID immediately
before each queued `ssh_write` IPC call. Chunks waiting behind previous
writes are discarded after Stop, disconnect, tab close or reconnect.
An input failure is shown only for the still-active session; an old
session's late error cannot replace a new session's status. Exact input
bytes, sequential ordering and the existing password/PAM prompt remain
unchanged. This does not undo bytes already delivered before cancellation.
Pure Node tests use only synthetic pending promises and session IDs.
Native Windows/Arch GUI acceptance remains **NOT TESTED**.

## 2026-11-19 — Explicit direct SSH agent forwarding (P1 SSH-07)

An opt-in checkbox allows forwarding the **existing local SSH agent**
for a single, direct, key-only SSH terminal session. It is **off by
default** and never written to the catalog, localStorage or recovery
data. Each Connect / reconnect requires a separate warning and explicit
confirmation before launching the session. Declining does not launch
a subprocess or forward the agent.

Native IPC validates the request independently: forwarding is permitted
only for TerminalKind::Ssh + AuthMode::Key with **no ProxyJump**.
SFTP, FilesAuth, local shells, password/PAM/Auto auth and jump chains
cannot enable it. The OpenSSH args retain strict host-key trust,
`-F none`, disabled multiplexing and `-oClearAllForwardings=yes`.
Only `-oForwardAgent=no` changes to `-oForwardAgent=yes`; no
untrusted host string or shell expression is interpolated.

**Security:** remote users with access to the forwarded agent socket
can request signatures/authentication on the user's behalf while
the session is connected; SSH private key material is not copied
by agent forwarding. Use only with fully trusted hosts and short-lived,
confirmation-constrained agent keys. NodeDesk cannot enforce restrictions
inside the local agent or prevent remote administrators from using it.
A suitable OS SSH agent must already be running; availability is
not automatically detected.

Rust argument-policy tests and Playwright confirmation/default-off/
password/ProxyJump/SFTP negative cases use no real agent or server.
A disposable actual-agent fixture and native Windows/Arch interactive
acceptance remain **NOT TESTED**. No credential forwarding is
automatically enabled.

## 2026-11-19 — Disposable real SSH-agent-forwarding integration

The Linux test fixture runs a loopback-only sshd with the existing
one-off host and client keys. A Rust integration test starts a new
ssh-agent in a temporary directory, loads **only the disposable client
key**, and makes two real key-only SSH connections to 127.0.0.1:22229
using the same restricted OpenSSH argv as NodeDesk:

- With forwarding disabled, remote `SSH_AUTH_SOCK` is absent and
  the test prints `AGENT_ABSENT`.
- With forwarding explicitly enabled, the remote shell can execute
  `ssh-add -l` through the forwarded agent and prints
  `AGENT_VISIBLE`.
- Host-key trust remains pinned to the disposable fixture file;
  agent forwarding is never enabled for jump hosts or other protocols.
  The test terminates the agent and sshd fixture at completion.

This proves protocol behavior **only for the disposable Linux runner**,
not the OS agent integration on native Windows or Arch, and not safety
against a compromised remote server. No real agents, user identities,
corporate hosts or stored credentials were accessed.

## 2026-11-19 — forwarded-agent second-hop authentication fixture

The disposable Linux SSH integration now verifies **actual key-based
authentication**, rather than just successful remote `ssh-add -l`.
The first SSH connection enters loopback sshd port 22229; from there
a second SSH client connects to another temporary sshd on port 22230.
Its identity is a **public-key-only** file with no matching private
key, combined with `IdentitiesOnly=yes`, strict host-key pinning,
password and keyboard-interactive authentication disabled, and batch
mode enabled.

When the first connection refuses agent forwarding, the second hop
must reject authentication. When the user explicitly enables forwarding,
the second hop must succeed and print the fixed sentinel. The test
supplies only the temporary agent's Ed25519 identity and two disposable
sshd host keys. All listeners use 127.0.0.1, and the fixture deletes
them afterward. This is an isolated Linux CI protocol test, not native
Windows/Arch GUI acceptance and not approval for general-purpose agent
forwarding to untrusted hosts.
