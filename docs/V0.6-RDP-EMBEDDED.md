# NodeDesk v0.6 — in-tab RDP via Apache Guacamole gateway

## What was implemented

The RDP tab now contains a second, opt-in mode for an **embedded Guacamole
desktop**. The browser client is `@pelotech/guacamole-common-js` 1.6.0, a
typed ES module built from Apache Guacamole 1.6.0 (Apache-2.0).

The display is physically rendered inside NodeDesk's Tauri WebView:
Guacamole canvas layers receive server pixels, and the mouse/keyboard can
send Guacamole input events. Includes read-only mode and manual
connect/disconnect. No window reparenting or detached local RDP viewer.

The preexisting `mstsc.exe` / `sdl-freerdp3` external launch option is still
available independently.

**This is gateway mode, NOT native IronRDP/FreeRDP inside the Tauri Rust process.**
The actual RDP protocol runs at an **independently configured Apache Guacamole
gateway (`guacd` and its authenticated tunnel server)**. NodeDesk only speaks
Guacamole's encrypted WebSocket protocol to that gateway. Neither guacd nor
the Guacamole application is installed or started by NodeDesk.

## Requirements / authentication

1. Deploy an Apache Guacamole 1.6.0-compatible gateway with a dedicated
   authorized RDP connection and a valid OS-trusted TLS certificate.
2. Authenticate to the gateway through its supported, configured policy
   **before** attempting to use the WebSocket tunnel. The NodeDesk viewer
   does NOT implement Guacamole's web-login endpoints, session cookies,
   or token management. A typical Guacamole installation requires an
   authenticated web-app session, and a Tauri WebView may NOT share the
   browser's cookies. Entering a public `websocket-tunnel` URL alone is
   **not sufficient to authenticate or select a connection** on an
   unmodified server. Gateway integration must be provisioned separately
   (e.g. an application-specific authorized tunnel, with tested cookie
   or other out-of-band authentication).
3. Enter the actual **wss://** Guacamole tunnel URL (not `rdp://` or
   `host:3389`). NodeDesk rejects user/password in URL, query tokens,
   fragments, cleartext `ws://`, whitespace and encoded path separators.
4. Click **Connect embedded**. The NodeDesk tab renders the remote
   framebuffer only if the gateway authorizes and establishes the
   connection. Use an authorized disposable Windows target for validation.

The HTTPS/WSS server certificate is validated by the WebView OS networking
stack. Guacamole gateway administrators are responsible for the RDP
destination, RDP server-certificate verification, NLA/authentication,
connection ownership, network isolation and gateway authorization policy.
NodeDesk **cannot independently verify** the RDP host's identity or
credentials through this mode. Gateway session success is not proof of
RDP server identity.

The NodeDesk UI never stores the supplied tunnel URL, passwords or gateway
tokens, and never appends tokens to URLs or local command-line arguments.
It uses the existing Guacamole session if the gateway authenticates it;
it does NOT prompt for RDP credentials inside NodeDesk. Clipboard and
local filesystem/device redirection are not wired to the UI.

### Why not directly embed IronRDP today?

IronRDP is a promising **native Rust RDP implementation** with a reusable
client crate and a bounded output-event API (images, pointer, lifecycle).
Its `ironrdp-client` currently uses the `ironrdp-tls` upgrade backend,
whose native-tls path enables `danger_accept_invalid_certs(true)` and
whose rustls path installs `NoCertificateVerification`. An application
cannot treat its client engine as a production-safe RDP connector merely
by reusing the default connection API. A real native NodeDesk backend must
add a certificate trust/pinning callback in the actual TLS handshake,
test changed/revoked certs, enforce NLA and policy, handle credentials,
and implement rendering/input/cancellation with secure data handling.
This investigation deliberately does **not** ship an insecure or
silently unauthenticated native connection.

## Automated QA and missing acceptance

Added URL validator unit tests and Playwright UI contracts that assert
that a catalog RDP tab does not autoconnect, does not accept tokens in
URLs, and leaves the external RDP launcher available. Both Windows and
Ubuntu frontend/Tauri builds validate packaging and Rust regressions.

**No CI environment contains an authenticated Guacamole 1.6 gateway and
real disposable Windows RDP host.** Build/UI contract tests cannot prove
a live RDP handshake, remote pixels, authentication, keyboard layout or
mouse responsiveness. Native and gateway connection acceptance is pending.

Acceptance must cover:
- TLS/certificate failures, unauthorized/expired gateway sessions and
  correct refusal with no credentials in URL.
- Connected authorized RDP host display and mouse/keyboard, focus and
  multiple tabs, read-only mode and disconnect-on-tab-close.
- Wrong RDP password, RDP server certificate changes and NLA failure as
  controlled by the gateway's configuration.
- Windows and Arch Tauri runtime, light/dark RU/EN, existing SSH/SFTP,
  VNC and system VPN regression checks.

## Next RDP engineering slice

1. Implement an explicit, authenticated Guacamole login handoff rather
   than assuming a desktop WebView shares the user's browser cookies.
2. Build a native IronRDP integration **only after** TLS server-identity
   verification can be enforced in its actual session. Then implement
   Tauri event/IPC framebuffer, keyboard/mouse and per-tab lifecycle.
3. Compare latency/quality/certification between the gateway and
   native engines, and keep either as an opt-in backend. `main` and the
   PR remain unchanged until user acceptance.
