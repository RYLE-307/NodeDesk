# NodeDesk v0.6 — embedded WSS VNC + external TigerVNC (draft PR #11)

## Working scope

A catalog connection can now use **VNC**, with default TCP port **5900**.
Opening its tab does not connect. Clicking **Open VNC / Открыть VNC** asks
NodeDesk's Rust backend to start a separate **TigerVNC Viewer** window with
the validated `host::port` target.

- **Arch/Linux:** requires system package `tigervnc` with
  `/usr/bin/vncviewer`. Install separately with
  `sudo pacman -S --needed tigervnc`.
- **Windows:** requires the official TigerVNC Viewer installed under
  `Program Files\\TigerVNC\\vncviewer.exe` (or the standard
  Program Files (x86) path). NodeDesk does not bundle or download it.
- Both OS variants use the same explicit TigerVNC command options.
- The VNC client window, sign-in, certificate validation and disconnect are
  **not controlled by NodeDesk**. Closing the catalog tab leaves that window
  alive. No network connection is made without the user's click.

The **external** mode remains TigerVNC with X.509-only schemes. The **new embedded**
mode uses noVNC inside the existing NodeDesk VNC tab, but requires a separately
configured **trusted wss://** WebSocket-to-RFB endpoint. It cannot connect
directly to a raw TCP:5900 service. No screen recording, file sharing, auto
reconnect manager, VPN/SSH tunnel manager, or embedded RDP yet.
See [embedded desktop architecture](V0.6-EMBEDDED-DESKTOP.md).

## Security defaults (intentional compatibility limit)

The **external TigerVNC launcher** requires X.509 certificate-based TLS with password/user
authentication: `-SecurityTypes=X509Vnc,X509Plain`. Ordinary `VncAuth`,
`None`, anonymous `TLSVnc` and insecure `Plain` are deliberately **not**
offered. If the server only supports those legacy methods, the connection
**fails closed** until a safe SSH/VPN tunnel implementation is available.

This policy is explicitly stricter than TigerVNC's broad automatic scheme
negotiation. The certificate trust UI belongs to TigerVNC. Verify the
certificate independently before accepting an unfamiliar key or certificate;
do not click through warnings without inspection. A server with a bad
certificate is **not** made safe merely by encrypting transport.

To avoid unintended transfer of sensitive workstation data, NodeDesk
disables clipboard receive/send and primary selection in the launched
TigerVNC viewer. Automatic viewer reconnect is disabled. TigerVNC prompts
for credentials; NodeDesk **never** accepts or stores VNC passwords. The
catalog's optional username field is not forwarded in this slice.

Only a verified single DNS name or IPv4 literal and TCP port 1–65535 can be
sent to the command. No URL, display suffix, option injection, shell,
argument expansion, password file or credential-bearing environment variable
is used. IPv6 VNC addresses, custom viewer paths and VNC gateways are not
yet exposed; the v1 catalog's validation does not support IPv6 literals.

## Verification

- Unit tests in `src-tauri/src/vnc.rs`: known-safe endpoint formatting,
  rejected malformed URLs/options/injected hosts and exact X.509-only
  command arguments.
- Catalog contract: VNC profiles round-trip in existing version-1 storage,
  unknown fields including passwords are dropped.
- Playwright: no automatic launch, explicit click/endpoint-only invocation,
  RU/EN messaging, failure handling and no false authenticated status.
- Windows/Ubuntu CI builds the native launcher and runs the v0.5 SSH/SFTP
  regression suite. **It does not run a real TigerVNC window or VNC server.**
- Manual Arch/Windows acceptance on a **disposable authorized VNC host
  with a trusted X.509 certificate** remains required before PR #11 is merged.

## Manual smoke test (after green CI)

1. Install the official viewer on your client system; do not change the
   system's VNC server automatically.
2. Create a VNC connection in the catalog (e.g. `vnc-test.lan`, port 5900).
   No password is stored. Check no viewer launches until the Open VNC button.
3. Launch and confirm the **X.509** server identity in TigerVNC before
   entering the test password. Confirm the remote screen responds.
4. Test denied authentication, wrong certificates and unreachable hosts.
   Confirm VNC does not automatically fall back to unencrypted transport.
5. Close the TigerVNC window; verify closing the NodeDesk tab alone does
   not claim to close the external connection.
6. Repeat RU/EN, light/dark themes, on Arch and Windows.
7. Confirm SSH/SFTP and RDP still work. Keep this PR draft until acceptance.

## Embedded mode manual acceptance (separate from external TigerVNC)

Use a disposable WSS-enabled RFB gateway with an OS-trusted TLS certificate.
Enter its `wss://` endpoint in the embedded viewer and click **Connect
embedded**; it must render the live framebuffer inside NodeDesk, not in a
separate application. Verify username/password authentication, mouse and
keyboard, Ctrl+Alt+Del, view-only, disconnect and tab close. Validate refusal
of `ws://` and URL-supplied credentials and TLS certificate errors. WSS
provides encrypted transport to the gateway, **not a guarantee that the VNC
origin server requires authentication**; the gateway must enforce its own
access policy and protect origin links. NodeDesk refuses an embedded RFB
session that finishes without a credential challenge. Unlike the external mode, noVNC
cannot be described as X509Vnc-only. Full limitations and license:
[embedded desktop notes](V0.6-EMBEDDED-DESKTOP.md).
