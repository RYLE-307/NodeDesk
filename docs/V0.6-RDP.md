# NodeDesk v0.6 — first RDP launcher slice

## Scope

The existing RDP catalog entries now launch an **external** operating-system RDP
client after an explicit click on **Open RDP / Открыть RDP**. No RDP connection is
opened when NodeDesk starts or the user opens a tab.

- **Arch/Linux:** uses `sdl-freerdp3` from the Arch `freerdp` package, with a
  native graphical password/domain and certificate confirmation flow.
- **Windows:** uses Microsoft's `mstsc.exe` with `/prompt /public`.
  Windows presents and manages credentials and certificate verification.
- **Optional Linux certificate pin:** an RDP profile may store the server
  certificate's SHA256 fingerprint as 64 hexadecimal characters, either plain
  or as 32 colon-separated byte pairs. NodeDesk normalizes it to lowercase
  plain hex and passes `/cert:fingerprint:sha256:<hex>` as one argument to
  `sdl-freerdp3`. Rust validates it again before spawning the client. The pin
  is ignored by `mstsc.exe`, whose arguments remain unchanged. An absent pin
  keeps FreeRDP's normal interactive certificate verification.
- Both receive a validated hostname/IP address and port. Linux additionally
  receives the optional non-secret username; Windows prompts for the username.
- An external client owns its window, authentication, certificate trust and
  disconnect. NodeDesk currently only starts it. Closing the NodeDesk tab
  does **not** kill an established external RDP session.

The **external launcher** is a deliberately modest functionality slice. The
same RDP tab now also offers a **Guacamole 1.6 embedded renderer** through a
separately installed authenticated **wss://** tunnel. This is not direct
TCP RDP or a native RDP engine. See [embedded RDP requirements](V0.6-RDP-EMBEDDED.md).

## Trust and credentials

NodeDesk passes **no passwords** via command line, environment, catalog,
persisted files, logs or IPC to the launcher. It also never supplies
`/cert:ignore`, `/cert:tofu` or disables encryption/authentication options.
The user must independently verify unexpected server certificate warnings in
the client's own UI before proceeding. FreeRDP's and mstsc's trust handling
is controlled by those clients, not by NodeDesk. No clipboard, drive, printer
or USB redirection is requested by the Linux launcher.

The Windows VM at `192.168.2.223` was reached from the native NodeDesk GUI on
Arch WSL2: the user saved the SHA256 pin in the RDP profile, clicked **Open
RDP / Открыть RDP**, signed in as `admin` in the external FreeRDP window and
saw the Windows desktop. The user supplied a screenshot of the visible desktop.
The fingerprint had been checked on Windows:
`b3:fd:df:e2:a1:35:b7:00:cd:0f:8d:a6:b7:15:fa:59:3e:5a:6f:56:7b:f5:c9:4f:c6:d0:10:32:03:d8:68:67`.
This confirms the external Linux launcher through the NodeDesk button on that
Arch WSL2 setup. It is **not** a test of native Windows `mstsc.exe` or the
embedded Guacamole viewer.

Hostnames must be DNS names or IP literals; invalid ports, URLs, whitespace,
control characters, injected options and malformed IPv6 are refused by the
Rust backend. Commands are spawned through the operating system without shell
interpolation. Windows is launched in public mode to avoid credential and
bitmap caching by mstsc. This does **not** imply that OS credential managers
or client-specific settings outside NodeDesk have been audited.

## Local acceptance

1. Confirm `main` remains at v0.5 and use the new v0.6 draft branch.
2. On Arch install the optional system prerequisite if needed:
   `sudo pacman -S --needed freerdp` (not installed by NodeDesk).
3. Add an RDP catalog connection to a disposable, authorized test machine.
   Open it: verify the native client's separate window appears only after
   clicking Open RDP. The NodeDesk tab must not falsely say authenticated.
   Completed on Arch WSL2 with `192.168.2.223`, saved SHA256 pin and `admin`.
4. Verify correct server/port and optional username, login, certificate
   warning/identity handling, desktop responsiveness and manual disconnect.
5. Repeat on Windows using mstsc.exe, including an invalid host, and ensure
   passwords were never entered or saved in the NodeDesk catalog.
6. Verify existing SSH/SFTP terminal/files functionality still works in
   the same workspace and RU/EN / light/dark themes.
7. Do not merge until CI completes and the user accepts both desktop targets.

## Automated tests

- Rust unit tests validate DNS/IPv4/IPv6, bad hosts/ports and exact per-platform
  arguments, ensuring there is no password or certificate bypass parameter.
- Playwright verifies explicit launch and failure messages in RU/EN and that
  the target contains only host/port/username. It uses a mocked Tauri call.
- CI compiles the native launcher on Linux/Windows and retains all existing
  v0.5 SSH/SFTP regression and isolated sshd tests.
- No CI claim of real authorized RDP login or cross-OS native GUI acceptance.

## Next v0.6 iterations

A gateway-based embedded Guacamole RDP frontend has now been added, but
requires a separately installed, authenticated Guacamole/guacd tunnel and
is not proven against a real Windows desktop. Native IronRDP/FreeRDP is
**not implemented**, pending mandatory TLS identity enforcement and NLA.
Existing RDP launches remain available externally. VNC now has an independent embedded WSS
viewer in draft PR #11; system VPN profile control is also implemented in the
same draft. See [embedded desktop architecture](V0.6-EMBEDDED-DESKTOP.md).
