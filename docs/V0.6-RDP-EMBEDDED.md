# NodeDesk v0.6 — in-tab Guacamole RDP with standard account login

## Implemented (draft PR #11)

NodeDesk's RDP workspace contains two independent options:

- **Embedded Apache Guacamole 1.6** client: Guacamole canvas layers render
  actual remote framebuffer data in the Tauri tab; keyboard and mouse send
  input to the authenticated Guacamole tunnel. User-controlled view-only and
  disconnect are available. Not a native RDP protocol implementation.
- **External mstsc/FreeRDP** launcher: direct RDP client outside NodeDesk,
  still available independently with its own password/certificate UI.

The embedded frontend uses `@pelotech/guacamole-common-js` 1.6.0 (Apache-2.0)
and requires a separate administrator-managed Apache Guacamole server/guacd
with a configured, authorized RDP connection. NodeDesk does **not** run guacd
or connect directly to RDP TCP port 3389.

## Standard Guacamole 1.6 sign-in workflow

1. Enter the HTTPS base URL of your Guacamole installation, such as
   `https://guacamole.example.org/guacamole/` — **not** a WSS URL,
   an RDP host, or a URL containing credentials.
2. Enter your **Guacamole account** username and password. The login is
   explicit, never automatic. NodeDesk sends `POST /api/tokens` with
   form-encoded credentials using HTTPS. Password input is cleared
   immediately; passwords are not saved to the connection catalog,
   localStorage, OS command line, app logs or environment variables.
3. Using the ephemeral token returned by Guacamole, NodeDesk enumerates
   authorized connections from each available data source through
   `GET /api/session/data/{source}/connections`, and offers **RDP
   connections only**. It does not list or activate a connection not
   returned by the authenticated server.
4. After the user selects one of those authorized connections and clicks
   **Connect embedded**, Guacamole's documented
   `/websocket-tunnel` endpoint is opened over encrypted WSS.
   The chosen connection ID/data source/viewport and temporary session
   token are passed as Guacamole's standard tunnel parameters.
5. Disconnect closes the active Guacamole client but leaves its account
   session available for reconnect. **Sign out** tears down the client,
   clears the token and selection from process memory, and attempts
   `DELETE /api/tokens/{token}` to invalidate the server session.
   Tab closure also attempts revocation. On a crash or offline sign-out,
   server-side expiry controls remain necessary.

### Deployment and security requirements

**Guacamole's standard 1.6 API necessarily places authentication tokens in
the REST/tunnel request URL query (or logout path).** Apache tracks this as
[GUACAMOLE-1818](https://issues.apache.org/jira/browse/GUACAMOLE-1818).
A WSS URL token is never displayed, logged by NodeDesk or persisted; it is
nevertheless visible to the Guacamole web application and to TLS-terminating
reverse proxies, which **must redact URL query strings in their access logs**.
The UI requires explicit acknowledgement before sending account credentials.
Guacamole session tokens are only kept in memory and are not fully
guaranteed to be erased from the WebView process after use.

NodeDesk's WebView uses the Guacamole REST API **cross-origin** and requires
the gateway/reverse proxy to allow **the precise Tauri application origin**
in its CORS policy, including POST/GET/DELETE endpoints and any preflight.
Do **not** use wildcard CORS with credentials or open it to arbitrary
websites. The frontend sends `credentials: omit` and relies on the
returned scoped Guacamole token. Confirm the deployment's origin and
CORS/TLS behavior on both Windows WebView2 and Linux WebKitGTK.

- HTTPS/WSS only: no cleartext HTTP/WS, URL-supplied passwords or
  arbitrary bearer-token query parameters typed by the user.
- HTTPS redirect-following is disabled for login and API requests;
  browser WebSocket TLS validation remains enabled.
- Guacamole account and RDP-host certificate identity, NLA/CredSSP and
  authorization policies are under the independent gateway's control.
  NodeDesk cannot vouch for the RDP server identity beyond the gateway.
- No clipboard synchronization, file redirection, smartcard or drive
  redirection is wired into the frontend. The gateway's RDP profile may
  have its own independent redirection settings, which administrators
  must audit.
- Authentication failure, CORS denial, expired tokens, invalid response
  data and inaccessible RDP connections must not silently fall back to
  unauthorized sessions or bypass TLS.

## Tests and remaining acceptance

Added unit tests for URL validation, auth response parsing, strict
selection of server-authorized RDP connections, HTTPS REST behavior,
query composition and secret handling. Playwright UI contracts check
explicit login, no automatic connection, denied bad URLs, RDP-only
selection, sign out and no localStorage persistence; a test-only WebSocket
stub validates the expected Guacamole tunnel request.

No automated integration environment currently has a live authorized
Guacamole gateway and disposable Windows RDP host. **Passing CI is not
proof of real framebuffer display or keyboard/mouse in a live session.**

Before merging PR #11, test on both Arch and Windows: authorized login,
connection selection, TLS/CORS restrictions, rejected passwords and
certificates, logout and token invalidation, actual remote image/input,
tab cleanup and disconnected/expired session behavior.

## Native embedded RDP remains a separate future backend

IronRDP client-engine integration is not shipped. In the inspected
`ironrdp-client-v0.1.0` source, the bundled `ironrdp-tls` backends allow
invalid server certificates by default. A native NodeDesk connector must
first enforce server trust in the actual TLS handshake (including changed
and revoked certificates), NLA policy, credential handling and session
teardown; only then should its native bitmap/input APIs be connected to
the Tauri WebView.
