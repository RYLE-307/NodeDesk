# v0.6 — embedded desktop architecture and security

This document separates **working code** from the planned RDP integration.

## Embedded VNC: implemented code, native acceptance pending

NodeDesk's VNC workspace now offers **two independent connection modes**.

1. **Embedded noVNC** (new): uses `@novnc/novnc` 1.7.0 (MPL-2.0).
   It displays framebuffer pixels and sends keyboard/mouse events **inside**
   a Tauri WebView tab. User initiates connection by clicking Connect embedded.
   The viewer can authenticate with a transient password, disconnect, use
   view-only mode, and send Ctrl+Alt+Del. A closing tab disconnects its RFB
   client. No remote operation is initiated just by opening a tab.
2. **External TigerVNC** (existing): launches the OS-installed viewer using
   the catalog host/port and restricted `X509Vnc,X509Plain` negotiation.
   Its separate window survives closing the NodeDesk tab.

### Embedded VNC transport requirements

The embedded noVNC client needs a **WebSocket that carries RFB bytes**.
**It cannot connect directly to a raw VNC TCP port 5900.**
The user must provision a WebSocket-enabled VNC server or a TLS-enabled
WebSocket-to-RFB gateway (for example, a properly configured websockify
deployment) with an **OS-trusted HTTPS/WSS certificate**.

- Enter an operator-controlled `wss://vnc.example.org/websockify` endpoint.
  The validator refuses `ws://`, `http://`, URL username/password, query
  tokens, fragments, control characters, and ambiguous encoded separators.
- The WSS address is **session only**: not in catalog, localStorage or a
  remote command line. An explicit button begins the connection.
- The WebView/OS validates the gateway's TLS certificate. Do not install a
  certificate-exception workaround or downgrade to cleartext WebSockets.
- **Authentication policy matters:** noVNC can negotiate legacy VNC
  authentication schemes, including `None`. WSS protects the connection
  against network eavesdropping and authenticates the gateway certificate,
  but it **does not guarantee the origin VNC server requires a password,
  that the gateway is trusted to forward to the correct server, or that
  origin-side transport is encrypted**. The embedded client now rejects
  a completed RFB handshake if the server never requested credentials,
  but that is not a substitute for gateway access controls or proof that
  the server enforced a strong authentication method. Operators must enforce
  authentication and restrict gateway access to authorized users.
  This mode does not claim the external TigerVNC client's X.509-only policy.
- Passwords are entered only on an ephemeral input when the VNC server asks
  for credentials. NodeDesk clears the input after handing it to noVNC and
  does not persist it or print it in logs. In-browser buffers are necessarily
  transiently readable in WebView process memory; forensic erasure is not
  guaranteed.
- The viewer never automatically copies clipboard data to or from the host.
  The browser's WebSocket implementation and the VNC server ultimately
  govern wire behavior. Browser-native cert verification failures may simply
  appear as connection errors, rather than prompting a trust dialog.
- noVNC identity-verification requests requiring interactive RSA pin
  confirmation are **rejected**, rather than silently approved.
- Before release, review applicable license notices:
  [noVNC MPL 2.0](https://github.com/novnc/noVNC/blob/v1.7.0/docs/LICENSE.MPL-2.0),
  [noVNC source](https://github.com/novnc/noVNC).

### VNC acceptance criteria

- Unit: safe/unsafe WSS URL validation.
- Browser: UI does not autoconnect; rejects cleartext URLs, secrets embedded
  in URLs, and query tokens; external TigerVNC path remains unchanged.
- **Pending native manual acceptance on Arch and Windows** with an
  *authorized TLS WSS VNC gateway and disposable VNC host*: verify
  certificate failure, password authentication, keyboard/mouse,
  framebuffer, view-only, Ctrl+Alt+Del, close/disconnect, and reconnect.
- Repeat on correct/incorrect credentials and RFB security schemes. Confirm
  that a gateway enforcing authentication and forwarding policy prevents
  unintended access.
- The separate disposable VNC lab supplies a real password-protected RFB
  peer and WSS gateway to Chromium CI. Native Tauri acceptance remains
  manual; see [VNC lab](../tests/vnc-lab/README.md).

## Embedded RDP: gateway code implemented, native backend NOT YET IMPLEMENTED

The new Guacamole 1.6 browser client provides an **in-tab framebuffer,
keyboard and mouse** through a separately installed Guacamole/guacd server.
NodeDesk now performs the standard HTTPS `/api/tokens` login and lists only
authorized RDP connections. A user must select one explicitly before the
Guacamole WSS tunnel starts. Credentials are not persisted, but Guacamole's
standard protocol **does require the temporary token in the WSS query**:
upstream reverse proxies must redact all query strings from logs. The UI
requires explicit acknowledgement. WebView-to-Guacamole REST calls also
require deployment-specific CORS for the exact NodeDesk origin.

This does not connect to raw TCP 3389, install guacd, or independently verify
the remote RDP host's certificate. The isolated GitHub Actions lab validates
a real xrdp session and Chromium canvas rendering over Guacamole with a
trusted disposable CA. After `ec5e646`, a user also confirmed visible Xfce
pixels, working mouse and `whoami` = `nodedeskqa` in native Arch WSL2
Tauri/WebKitGTK over HTTPS/WSS. Real Windows RDP hosts and native Windows
Tauri/WebView2 remain outstanding. See the
[isolated lab](../tests/guacamole-lab/README.md).

**Native embedded FreeRDP/IronRDP is not wired.** IronRDP's native-tls
and rustls backends in the referenced v0.1 client tag currently skip
certificate validation by default. We will not enable a native session
until TLS identity validation and NLA can be enforced at the TLS handshake.

[Detailed gateway and native backend assessment](V0.6-RDP-EMBEDDED.md).
