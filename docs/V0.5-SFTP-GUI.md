# v0.5 SFTP GUI — Linux and Windows authentication review

## Windows native password / keyboard-interactive slice (PR #10)

Windows interactive Files login now uses Rust `ssh2`/libssh2 (Cargo.lock pins
the resolved versions), not Unix ControlMaster.
The build explicitly enables both vendored-openssl and openssl-on-win32:
vendoring alone does not select OpenSSL instead of the default Windows CNG
backend. Windows CI deliberately uses an ECDSA peer; Linux uses Ed25519 sshd.
Auto and Password/PAM try
keyboard-interactive, then password if offered. Each remote operation opens an
SFTP subsystem channel on the authenticated connection and feeds the existing
binary SFTP v3 client. Direct OpenSSH key/agent and both interactive consoles
are preserved; Linux keeps its existing OpenSSH auth bridge.

Before requesting ANY credentials, the negotiated raw host key must match
OpenSSH known_hosts. The adapter invokes `ssh-keygen -F` with only the public
host/port and trust-file path (no shell). This preserves OpenSSH hashed-host and
pattern matching. Stores: user ~/.ssh/known_hosts and Windows
%ProgramData%/ssh/ssh_known_hosts. Missing stores mean unknown; unreadable stores,
lookup failures, changed/conflicting same-algorithm keys and all matching
@revoked or @cert-authority entries fail closed. Multiple ordinary key algorithms
are allowed, but the negotiated algorithm must have an exact trusted key.
Certificates/CA trust and known_hosts2 are unsupported, not silently trusted.
First trust remains in the existing OpenSSH console after independent fingerprint
verification. No automatic acceptance, StrictHostKeyChecking relaxation or
credential-bearing argv/environment/askpass is introduced.

Password/PAM challenges use the existing embedded login terminal. All responses
are hidden, including server prompts marked echo=true. Displayed challenges strip
terminal control characters. Input is bounded (4096-byte answer, 32 queued input
chunks, 16 prompts per callback), supports backspace and Enter; Ctrl+C/Escape or
Disconnect cancels. Auth prompts have a 120-second deadline; SSH I/O has a
15-second timeout. Client-owned secret strings are cleared where practical, but
WebView/IPC/libssh2 buffers cannot guarantee forensic memory erasure. Credentials
are never persisted by the application or placed in diagnostics, telemetry,
process arguments or environment. No shell or forwarding channel is requested.

Cancellation/timeout interrupts the underlying native TCP connection, so it closes
the whole Windows Files login; the user must reconnect. Linux cancellation still
preserves its master login. EOF/I/O errors invalidate native readiness. Disconnect,
tab close and app-window close shut down the socket, including an auth prompt.
Transfers retain binary data, no-overwrite, partial-file behavior and sequential
50-file queue semantics; completed files are never rolled back.

Explicit limits: no native key/agent/private-key picker in interactive Windows
mode (uncheck the login option for existing OpenSSH key/agent); no certificate/CA
trust, password-change flow, arbitrary mixed-method MFA chain or saved credentials.
Keyboard-interactive supports repeated/multiple challenges, but real OTP/vendor
MFA deployments still require acceptance. DNS resolution uses the OS resolver;
its timeout is OS-controlled. No manual Arch/Windows GUI acceptance is claimed.

Verification is split deliberately: Linux CI runs the native adapter AND the
unchanged Linux bridge against isolated real OpenSSH/sshd with a disposable PAM
account. Windows CI runs the native adapter against an independent Paramiko
loopback SSH/SFTP peer, exercising password and keyboard-interactive, trust
negatives before prompts, binary round trip, collisions, mkdir/rename/rmdir and
transfer cancellation. That Windows peer is NOT Windows OpenSSH server or real
PAM. Unit tests cover hidden input, cancellation and destination binding;
Playwright covers Windows capabilities, password-mode gating, disconnect, RU/EN,
themes and queue regressions. Integration tests return early without the fixture
environment; the dedicated CI fixture steps supply it. Full desktop acceptance
against the user's server remains pending and PR #10 stays draft.

Adapter references: [ssh2 Session/auth callbacks](https://docs.rs/ssh2/0.9.7/ssh2/struct.Session.html),
[Channel binary I/O](https://docs.rs/ssh2/0.9.7/ssh2/struct.Channel.html),
[OpenSSH host matching](https://man.openbsd.org/ssh-keygen#F).
Dependencies and redistribution: ssh2-rs MIT/Apache-2.0, libssh2 BSD-3-Clause,
vendored OpenSSL Apache-2.0, zlib license, base64 MIT/Apache-2.0, zeroize
MIT/Apache-2.0. Source package license notices must accompany final binary
distribution; no release binary is published by this draft.


Implemented: independent local/remote panels, explicit path/refresh/up and folder
navigation, selection, name/type/size/mtime/mode, binary upload/download,
confirmation, no-replace publication, byte progress and cancellation. SSH and SFTP
consoles stay mounted when switching tools. Opening tabs starts no operation.

## Transport and security

System OpenSSH `ssh -T -s … sftp` transports binary SFTP v3 packets. The structured
adapter follows the [protocol draft](https://www.openssh.org/txt/draft-ietf-secsh-filexfer-02.txt),
checks lengths, request IDs, attribute flags and UTF-8, and ignores `longname`.
It never parses CLI listings or interpolates filenames into shell commands.
The direct OpenSSH path verifies known_hosts including changed/revoked keys.
Configuration, shell commands, forwarding and multiplexing are disabled.

Linux Files now offers a native OpenSSH authentication bridge: select Auto,
Key/agent or Password/PAM in the Files login panel, connect, verify the host
fingerprint through a trusted channel if new, and enter credentials at the hidden
OpenSSH PTY prompt. Wait for “Authenticated — panes ready”, then load both panes.
The terminal deliberately has no shell prompt after successful login.

The bridge runs OpenSSH with ControlMaster=yes, ControlPersist=no and -N -T.
Its exclusive /tmp/nd-<UUID> directory is created with mode 0700. The socket is an
authenticated-session capability, not a credential file. The backend binds it to
the original host, port, username and live session; the frontend cannot provide
an arbitrary socket path. SFTP retains separate binary stdin/stdout pipes.
A false proxy makes a missing master fail closed, without fresh authentication
or a different connection. Disconnect/tab/window close kills the master; an
uncompleted auth prompt times out after 120 seconds. Abrupt crashes can leave an
empty directory/socket; no automatic broad /tmp cleanup is performed.

Host trust remains OpenSSH StrictHostKeyChecking=ask on the auth PTY, including
changed/revoked-key rejection; the direct key/agent path remains strict=yes.
No bypass or automatic acceptance. Trust is checked when the master connects;
an already established SSH session is not re-authenticated for each operation.
Passwords/OTP/passphrases pass transiently from the terminal input through Tauri
to the native PTY. They are not stored in React state, localStorage, files,
process arguments, environment, logs, commits or telemetry. JavaScript/OS buffers
cannot promise forensic memory erasure. The private socket authorizes access to
the same account until disconnect; same-user compromised processes are outside
the isolation boundary. No agent forwarding, shell command or remote PTY.

Windows interactive Files login uses the native adapter described above; uncheck
interactive login for direct OpenSSH key/agent. Existing SSH/SFTP consoles remain.

Transfers use loaded paths, not unsent address-bar edits. Both panels must be
loaded. Explicit confirmation shows direction/name/destination; the backend also
enforces no-replace semantics, independently of stale listings. A profile edit
invalidates remote state. Closing the tab cancels its action; closing the window
kills/reaps registered children. Cancellation and timeout kill the process to
unblock pipe I/O. Cancellation cannot roll back an already committed publication.

Upload exclusively creates `.nodedesk-<UUID>.part` (0600), acknowledges every write,
checks size and closes before ordinary SFTP v3 RENAME. Per the protocol, rename
must fail if the final name exists; never use the overwriting posix-rename extension.
A failed/cancelled upload may leave this named partial; the error reports it.
Cleanup is manual through console, avoiding deletion of a replaced remote path.

Download rejects known symlinks/existing final names, writes a private exclusive
local partial, checks byte count, syncs and hard-links to the final name atomically
without replacement. For **single-file downloads**, RAII removes the partial on
success/failure/cancel. For **explicit batches**, a partial is now retained on
failure/cancellation for optional verified resume in the same tab and removed
after successful publication. A crash may leave a partial. Hard-link support
(ext4/NTFS) is required; FAT/exFAT
fails safely. Permissions/mtime are not preserved. Same-length concurrent source
changes are not detected: hash-check files modified during a transfer.

### Follow-up in draft PR #11 — safe read-only remote text preview

Explicit **Preview text** in the remote SFTP pane reads one regular remote file
through the same previously trusted SSH/SFTP session, with a 128 KiB hard limit.
It rejects symlinks, binary/NUL, invalid UTF-8, unsafe control characters,
unknown file size and detectable changes in size/mtime while reading. Rendering
is plain React text (not remote HTML). Closing the preview, switching the SSH
profile, or losing interactive login clears the displayed data. The operation
is cancellable and has the existing 120-second watchdog. No edits, automatic
file reads, local temp files, overwrites or persistent content storage.
**Do not preview files containing credentials**: remote text is shown transiently
in the WebView. Unit + isolated real-SFTP fixture + browser tests were added;
real desktop acceptance on Windows/Arch is still outstanding.

### Follow-up: in-memory editor and non-destructive Save as new copy

The user can explicitly switch a preview into an in-memory text editor and
choose **Save as new copy**. The backend rereads the source and compares its
complete UTF-8 contents against the original preview, then uses SFTP v3
`SSH_FXF_CREAT | SSH_FXF_EXCL` to create a *different* name. It never writes
to the source file or overwrites an existing file. The new copy is reread to
verify its contents; the original is reread and concurrent changes are
reported. There is no implicit save, OS temp file or localStorage write.
Changing directory or closing unsaved edits requires confirmation; losing
authentication/profile clears transient text. Cancelled or failed writes
may leave a partial **new copy**; investigate its name rather than assuming
automatic cleanup. Text size is capped at 128 KiB and only valid UTF-8 without
unsafe controls is accepted.

**Important:** SFTP v3 has no native atomic conditional-replace operation,
so this does **not** overwrite/update the original in place. That would be
unsafe under external concurrent edits without extra server-side support.
Full remote-editor parity, version conflict recovery, encoding selection,
manual desktop QA and safe source replacement remain open.

### Follow-up: local literal find and replace (draft PR #11)

The in-memory UTF-8 editor has **Previous/Next match**, exact-selection
**Replace selected**, and explicitly confirmed **Replace all**. Search is
case-sensitive, literal (no regex), and does not read files or contact a
server. The UI limits terms to 256 UTF-16 units, at most 4096 replacements
per action and 128 KiB UTF-8 for resulting text; Rust validates content
again when Save as new copy is separately invoked. No automatic saving.
Switching to the read-only view does not discard pending edits; closing or
leaving the remote folder still asks before losing them. Profile/auth loss
clears transient contents rather than exposing them in another session.
Node/browser tests cover Unicode offsets, wrap-around, literal metacharacters,
cancellation of replace-all and absence of a save request. Native Windows
and Arch GUI acceptance remains outstanding.

## v0.5 follow-up: bounded filesystem mutations and internal drag-and-drop

In this review branch, both panes now provide New folder, Rename and Delete controls. Rename requires a previously loaded, selected regular file or directory; delete is **permanent** and requires explicit confirmation showing the filename, parent folder and the non-recoverable nature of the action. No recursive deletion, no symlink mutations, no copying directory trees. Remote SFTP v3 uses the actual MKDIR (14), RENAME (18), REMOVE (13) and RMDIR (15) requests. Server-side LSTAT revalidates the expected entry kind; rename checks that the new filename is absent and uses ordinary v3 RENAME, **never** the OpenSSH overwrite extension. RMDIR succeeds only for an empty remote directory. On SFTP servers that violate v3 semantics or under hostile concurrent writers, a pre-check is not a fully atomic universal no-overwrite guarantee; do not rename important files without backups.

Local mkdir uses create_dir; delete supports regular files and empty folders, refuses symlinks and non-matching entry types. Local regular-file rename uses exclusive hard_link + unlink to prevent destination clobber on supporting filesystems. Local **directory rename** now uses Linux renameat2(RENAME_NOREPLACE) and Windows MoveFileExW without REPLACE_EXISTING, never plain std::fs::rename (which could overwrite on Unix); unsupported kernels/filesystems fail closed. Directory move is same-volume only; the source can still change between an initial LSTAT and the syscall in an adversarial writable directory. Hardlink-based *file* rename is not an atomic move: if removing the old name fails, both names may remain. FAT/exFAT may reject hardlink operations.

Two-pane internal Drag & Drop transfers **single selected regular files** between *loaded* panes. The drop target and source directory are validated and the same explicit upload/download confirmation/no-overwrite check is used as the buttons. External OS file drops, directory recursion and bulk selection are unsupported. An incomplete upload can still leave a marked remote `.nodedesk-*.part` file; cancel cannot undo a committed mutation.

Tests: Rust local mutation tests include invalid names, existing-name collision, no-clobber, nonempty directories and type rejection. Real sshd SFTP integration verifies remote mkdir, rename, destination collision and nonrecursive delete in a disposable directory. Playwright UI contracts cover prompts, confirmation, readiness gating, existing-name rejection and internal drag collision. **Manual full GUI verification on Arch and Windows remains pending**; the existing verified Linux password/PAM fixture is not evidence of all graphical user flows.

## Automatic pane refresh after successful actions

After a successful upload/download or mkdir/rename/delete, NodeDesk invalidates
the destination listing and reloads **only that pane** from the backend. The
refresh is a separate, user-initiated-session operation after the mutation's
operation gate is released; it does not reopen a disconnected login or start
new sessions automatically. Cancelled, failed, stale-profile and unmounted
operations do **not** trigger a refresh. If the refresh itself fails, the pane
remains unloaded and the error is shown; the mutation is not repeated.

The other panel (including its selection) stays unchanged. This behavior is
covered by an additional Playwright contract test for upload and mkdir.

## File list searching and sorting

Each loaded file pane now has a **local, case-insensitive filename filter**.
Typing narrows the current listing without requesting a new SSH/SFTP
connection, and clears any selected row so a hidden item cannot be
accidentally uploaded, downloaded, renamed or deleted. Folders sort before
files/links, with natural numeric ordering among names. The full loaded
listing remains authoritative for backend operations and drag/drop checks.
The filter does not search the entire server filesystem or recursively
walk directories. The filter is not persisted in catalog profiles.

## Bounded multi-file transfer queue (new review slice)

The GUI can select multiple **regular files** in a loaded local or remote pane
using checkboxes (limit: 50 files per operation). The **Upload selected** and
**Download selected** actions confirm the complete batch before any transfer.
The client validates every selected name and aborts the entire queue if any
name collides in the currently loaded destination listing, is unsupported, is
not a regular file, or one pane is not loaded. The Rust backend also rechecks
paths, source types and destination exclusivity for **every** file.

Files transfer **sequentially**, never concurrently. The queue stops on the
first failed file or on cancellation and never silently skips or retries.
There is one progress bar for the current file plus a displayed item index.
The Cancel button requests cancellation of the active native operation and
prevents starting remaining files. Files already successfully published are
**not** rolled back; if the batch is interrupted after partial completion,
the destination listing is invalidated to avoid showing stale information.
A successful batch reloads only its destination pane. No queue persists or
resumes after the tab or app is closed, and no credentials or filenames are
persisted outside the existing catalog.

This is an intentionally small queue, **not** a background transfer manager:
no resume/retry, transfer history, bulk directory traversal, external OS file
drop, transfer speed aggregation or background priority controls.

Verification: pure-model tests cover collisions, limits, source types, duplicate
selection and non-mutating planning; Playwright UI contract tests cover two-file
sequential upload and cancel during the first file. CI also runs the existing
real-sshd binary transfer/host-trust fixture, but those UI queue tests use a
mock adapter and cannot prove real user-server GUI access. The latest CI and
manual Arch/Windows GUI acceptance are required before merge.

## Transfer queue outcomes and selected-file drag

The current review branch exposes a **session-only per-file report** with states
Queued, Transferring, Done, Failed, Cancelled and Not started (also translated
into Russian). Closing the tab or changing the connection discards the report;
it is never written to storage or telemetry. The current queue index now uses
the actual number and filename rather than the literal placeholder string.

For a batch, every file is still transferred sequentially with the existing
binary SFTP transport, no overwrite and explicit batch confirmation. On
cancellation, any unstarted files are marked **Not started**, not falsely
reported as successful. Successfully committed files remain in place and are
not rolled back. A failed item stops subsequent transfers; the user can
reload the destination before attempting another batch.

**Select visible (up to 50)** chooses eligible regular files from the currently
filtered listing. Dragging one of the chosen files to the opposite pane sends
the chosen set through the same bounded batch validation/confirmation path.
Dragging an unselected file sends only that one file. Invalid drag payloads,
same-pane drops, duplicate names and unsupported paths are rejected before
invoking the backend; the backend independently checks type and destination.

The report remains **session-only** and is not a durable transfer history,
persistent queue or byte-level resume. In draft PR #11, the user can explicitly
choose **Retry unfinished** after a failed/cancelled batch. The action requires
both panels refreshed since the last attempt, same SSH destination and folder
paths, original source type/size/mtime/permissions metadata unchanged where
reported, and all remaining names collision-free in the destination. It
rechecks these conditions using the existing backend upon every transfer.
The user confirms the exact retry list before any network write. Items already
marked **Done** are skipped; Failed, Cancelled, and Not started are retried
sequentially, each **from byte zero**. A `.nodedesk-*.part` left by a cancelled
upload is not reused or automatically deleted. If a source changed, initiate a
new queue after review instead of bypassing checks. Retried files can still
fail after the fresh listing (TOCTOU), so no overwrite protections are relaxed.
Closing the tab or switching connection drops the ephemeral queue.

This is **safe per-file retry**, NOT resumable byte ranges, a durable background
queue or a guarantee against changed same-size source bytes. Resuming partial
uploads/downloads safely needs authenticated source and partial prefix
validation, stable checkpoints, and a failure/cleanup policy that do not yet
exist. Tests cover model invariants and mocked GUI retry/refresh/collision
gates; latest CI and real Arch/Windows desktop acceptance are still required.

## Native Windows SFTP authentication capabilities

The app now queries the Rust backend for supported file authentication methods
via `files_capabilities`. On native Windows OpenSSH the interactive Unix
ControlMaster socket bridge is not available, so the GUI **defaults to
key/agent mode** and disables the unsupported password/PAM checkbox with
a clear RU/EN explanation. Password authentication remains available in the
separate SSH and SFTP *terminal* tabs (via a native PTY). Linux continues to
show interactive password/PAM in the Files panel by default.

No OS is inferred from the WebView user agent; the native backend reports
its actual capability. Neither path relaxes OpenSSH `known_hosts` trust.
The request does not collect, copy, cache, or log any credentials.
The capability check does not silently attempt password login or start a
network connection. Automated browser contracts cover Windows/Linux
presentation and ensure that Windows does not spawn an unsupported SSH
ControlMaster bridge. Rust tests verify capability flags.

This is a **safer fallback, not implementation of Windows GUI password**.
A real Windows password/PAM file browser needs an audited transport
architecture that does not depend on Unix ControlMaster or expose passwords
through arguments, environment variables, logs or persistent storage.

## Explicit verified SFTP upload resume (draft PR #11; not persistent)

A stopped upload may leave a server-side partial named
`.nodedesk-<operation-id>.part`. The current tab retains that operation ID
only for the failed batch item. The user must refresh **both** panes and
confirm **Resume verified upload**. Successful files are never replayed.

The Rust SFTP client reads the existing partial and compares **every** remote
prefix byte against the same local source byte before opening it for writing.
A missing, symbolic-link, zero-length, oversized or mismatched partial fails
without writing. On a match it writes **only the missing suffix**, using
SFTP write without CREATE/TRUNC/APPEND, then reopens the entire remote file
and byte-compares it to the local source before non-overwriting publication.
The original local file is never opened for writing.

Failure or cancellation can leave the partial on the remote server; it is
not automatically deleted or trusted on subsequent attempts. Ordinary
**Retry unfinished** still starts each incomplete file from byte zero.
By default no transfer plan is retained across restart; the opt-in checkpoint described below preserves bounded metadata for manual recovery only. SFTP v3
cannot prevent every concurrent remote race or guarantee server honesty;
this feature is not safe against an actively hostile remote filesystem.

Real disposable OpenSSH/SFTP fixtures test success, corrupted prefix,
destination collision, and integrity of the resulting binary file; browser
tests check explicit confirmation and operation ID reuse. Manual native
Windows/Arch GUI acceptance, download resume and persistent/checkpointed
resume remain open.


## Verified download resume (draft PR #11; current tab only)

**Download selected** retains a private local `.nodedesk-<operation-id>.part`
when its batch is cancelled or an item fails. A **single-file download** still
removes its partial on normal failure. The user may manually refresh BOTH
local/remote panes, review the unchanged source metadata and destination,
then explicitly confirm **Resume verified download** for the latest incomplete
download. Done files are never downloaded again; other pending items start new
transfers as before.

The native operation checks the local final name is absent, the partial is a
regular file (Linux O_NOFOLLOW / Windows reparse-point-safe reopen, plus file
type/inode checks), has exactly one local hard link on Unix and a nonzero size
no greater than the known remote source size. It uses trusted SFTP reads to
compare **every retained prefix byte** against the remote source before
opening the local partial for writing, then appends only missing remote
bytes. For a full-sized partial, it just verifies without downloading more.

After syncing, it verifies that the remote source metadata remains consistent
and rereads the **entire remote file** to compare it against the complete
local partial. Only a matching file is published with an exclusive local
hard-link (never rename-overwrite), and the partial is then removed.
A mismatch, unsafe partial, lost connection or collision refuses publication;
the previously downloaded partial may be left for inspection. No automatic
retry/connection or silent cleanup of failed batch partials is included.
The opt-in checkpoint described below supports manual recovery after restart,
not automatic transfer or a persistent background worker.

The tests exercise real disposable OpenSSH/SFTP byte-offset transfers on
Linux/Windows, corrupt/unsafe partial rejection, and Playwright-only manual
confirmation and operation-ID handling. Native Windows/Arch GUI acceptance,
interrupted multi-gigabyte transfers and changing remote sources require
further testing. Protection against malicious concurrent local processes or
an untrusted SFTP server is not guaranteed.


## Opt-in SFTP queue recovery metadata (draft PR #11)

The user can enable **Keep unfinished queue for recovery after restart**
BEFORE starting a 1–50-file batch. Default is **off**. The WebView stores a
versioned, bounded checkpoint for the newest unfinished batch per SSH endpoint
(up to 8 endpoints, 7-day expiry). The serialized fields are: host, port,
username, local and remote directories, filenames, original source file
type/size/mtime/mode, per-file completed/unfinished status, latest partial
operation ID, and checkpoint time.

**Important privacy tradeoff:** these names, local paths and host identities
are saved in plaintext application local storage. Do not opt in on shared
devices or when filenames/path information is sensitive. No passwords, private
keys, SSH authentication session IDs, open handles, file bytes, remote editor
drafts or VPN credentials are persisted. Users can select **Forget saved queue**
to delete only the checkpoint metadata. Existing on-disk or server-side
`.part` files remain until manually inspected/removed.

The frontend writes a snapshot before each file starts and after each state
transition. If it crashes while a file is active, that file is restored as
**Cancelled**, queued items become **Not started**, and successful files stay
**Done**. Upon relaunch, only a notice with a **Load saved queue** button is
displayed. It does NOT initiate a login, list directories, read partials,
start an upload/download or restart a queue.

Recovery workflow: authenticate normally first, manually load the saved
checkpoint, refresh BOTH local and remote filesystem panels, and confirm
**Retry unfinished** (from zero) or **Resume verified upload/download**
when an eligible partial exists. The existing source metadata/destination
collision checks and full-prefix byte-verification remain mandatory.
If any check fails, NodeDesk refuses automatic fallback or overwrite. A new
batch can replace the old checkpoint only after confirmation.

Recovery is limited to the latest unfinished batch **per endpoint** and does
not provide unattended/scheduled transfers, a durable multi-queue execution
engine, a guaranteed server snapshot, a clean-up service for abandoned partials,
or cryptographic protection of checkpoint metadata. Manual desktop acceptance
on Windows/Arch and interruption testing over unstable networks are pending.

## v0.8 functional development: guarded remote POSIX permissions

The Files context menu offers **Change permissions…** only for an explicitly
selected remote regular file/directory whose listing includes POSIX permission
metadata. It sends a separate, explicitly confirmed SSH/SFTP v3 SETSTAT request.
The input must be a normal three-digit octal mode 000–777 (optional leading
zero); setuid, setgid, sticky and arbitrary attributes are forbidden. Changes
that enable world-wide writes require a visible warning. No shell or sudo is
used. The local/Windows filesystem's ACLs are never modified by this command.

The Rust backend validates the name/canonical parent, checks the selected
entry is still the same regular file/directory (kind, full mode, size and
modification time), and rejects changed metadata, symlinks and special bits.
It rechecks the type and final permission bits after SETSTAT. Only then does
the GUI refresh its remote listing. SFTP v3 SETSTAT is path-based and cannot
be made atomic with LSTAT against a malicious concurrently changing server
filesystem; do not use this as a security boundary on untrusted servers.

Automated tests cover octal validation, explicit confirmation/no accidental
network writes, packet framing, symlink/stale-metadata refusal, and an actual
disposable Linux OpenSSH/SFTP chmod operation. Native Windows/Arch GUI tests
are intentionally deferred to the consolidated v0.9–v1.0 acceptance campaign.


## Agent-only single-hop Files gateway (2026-11-08)
An optional transient gateway host, username and port now allows a single
OpenSSH ProxyJump hop for GUI SFTP key/agent operations. Files refuses
interactive login in gateway mode. An explicitly selected key file
is permitted for the target only, while the gateway uses agent/default keys. Both hosts must be trusted in advance. The target uses strict
host-key checking, while the gateway's OpenSSH child may use local ssh_config
even though the target specifies -F none; audit the gateway configuration.
No auto-connect, saved secrets, agent forwarding or arbitrary gateway chains.
Real two-hop integration and native Windows/Arch acceptance remain NOT TESTED.


### Disposable gateway integration details
The Unix fixture uses a private ssh_config file for its two nested OpenSSH
processes, replacing production -F none **only within the test command**.
The actual ProxyJump child authenticates against the ephemeral sshd and the
binary SFTP client lists the target. A second handshake rejects an untrusted
target while gateway trust stays intact. The test never edits real known_hosts
or accesses any outside network. Native Windows/Arch and two independent
hosts remain untested.


## Two-hop disposable fixture (2026-11-08)
The isolated Ubuntu integration fixture starts three loopback-only sshd
listeners on distinct ports, executes OpenSSH's real two-hop ProxyJump,
and performs binary SFTP realpath/list. It then removes the middle hop's
host key from an isolated known_hosts file and requires strict rejection.
This does not prove behavior with three physically distinct hosts, a
corporate gateway, or a native Windows/Arch GUI session. Never use the
fixture against production SSH destinations.
